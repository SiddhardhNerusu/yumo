## M0 — Fix the prediction foundation (NEW — precursor to M1) — M

**Why this exists.** v1's M1 assumed the Brain can predict a real user's real food. It cannot, and what it does instead is worse than nothing. Two verified facts:

1. **A real user's own foods can't reach the nudge, because they're never on the only menu.** `nextNudge` fires via `tier === 'high'` or `coldStart && breakdown.menuPrior > 0` (predict.ts:102-104), and **`menuPrior` is the load-bearing term** — without it a strong habit tops out at tier `medium`/`fire:false` (the repo's own test: *"a habit with no menu backing lands in tiles, not a proactive nudge"*, predict.test.ts:33-37). ⚠️ The precise problem is not that high tier is unreachable — a menu-aligned habit reaches it fine (verified: a 21-day `greek_yogurt` breakfast scores **0.837, tier high, fire true**). It is that **the only menu fed to the Brain is `SEED_MENU` (demo foods)**, so a *real* user's foods never get `menuPrior` at all. Making the real generated menu feed `menuPrior` (step 2) is therefore the whole point of M0.
2. **A day-0 real user gets nudged about food they have never eaten.** The only menu fed to the Brain is `SEED_MENU` (useToday.ts:112,116 and widget/payload.ts:34) — built from `HABIT = {greek_yogurt, chicken_rice, salmon_veg, apple_pb}` with the comment *"Menu covers every day so menuPrior fires whatever today is (static)"* — and it is **not gated behind `DEMO_DATA`**. A new user is `coldStart` with `menuPrior = 1` on all four ⇒ `fire: true, framing: 'menu'`.

That directly breaks the promise `demo.ts:1-11` makes: *"A real user (including a TestFlight dogfood build) must start with an honest, empty slate… never a fabricated persona."* **WS-6 (`87bb891`) gated the seed history, starter fridge and weight trend; `SEED_MENU` leaked through.** This is a live bug in build #5, independent of M1 — and M1 would take the same wrong prediction to the lock screen.

1. **Gate the demo menu.** `useToday.ts` and `widget/payload.ts`: `SEED_MENU` only when `DEMO_DATA`. Production passes the real menu (step 2) or `undefined` (`PredictInput.menu` is already optional, predict.ts:12-24).
2. **Adapter: real menu → Brain menu.** New `app/src/data/menuBridge.ts`: `weekMenuFor(plan: WeekMenuPlan): WeekMenu` — map `plan.days[].picks[]` → `{dayOfWeek, slot, foodId, portionG}`. Ground truth: `plan.days[i].dayOfWeek === i` always (generate.ts:278, fixed Sun…Sat); `MenuDay { dayOfWeek, picks, totalKcal, totalProtein_g }` (types.ts:63-75). Day already holds the plan (`Day.tsx:92` `getMenu(profile,…).then(r => setPlan(r.plan))`) — thread it into `useToday` as a new optional arg, defaulting to today's behavior when absent so nothing else moves. ⚠️ **Thread it into `widgetPayload` too** (see step 4 and M1 Phase B) — the widget shares this menu-alignment problem, and without the real menu it can never produce a suggestion in production.
3. **Lift the resolver.** `resolver(events)` (useToday.ts:89-100) is **private** and is the only name/kcal resolution: `FOODS[id]?.name ?? fromLog.get(id)?.name ?? id`. Move it to `app/src/data/resolveFoodMeta.ts` and use it from `useToday`, `widget/payload.ts` (which today reads `FOODS[…]` only, :48-50 — so an `fdc:` or `my-*` food renders a **raw id at 0 kcal**), and M1's notification copy. **Do not write a fourth copy.**
4. **Bring `payload.ts` onto the live path:** it must take the **real menu as a 4th arg** — `widgetPayload(events, now, budget, menu?)` — and use `buildCandidates` (not the static `CANDIDATES[slot]`, :29-30 — `candidates.ts:6-7` literally says it "Replaces" it), `getBrainConfig()` (not `DEFAULT_CONFIG`, :35), the lifted resolver, and gate `SEED_MENU` behind `DEMO_DATA` (step 1). Without the menu arg, `menuPrior = 0` in production ⇒ `nudge.fire = false` for every non-cold-start user ⇒ `suggestion = null` forever, which is exactly what would make M1 Phase B's "widget shows a real prediction" acceptance unmeetable. M1 Phase B.4's call becomes `widgetPayload(events, now, budget, weekMenuFor(plan))`.
5. **Do NOT touch the ladder threshold.** `DEFAULT_LADDER.nudge = 0.75` is remote-tunable (server/src/config.ts:46) and high tier **is** reachable for a menu-aligned habit (~0.84 observed). Once the real menu feeds `menuPrior`, **report the observed fire rate**; only if it is implausibly low is that a **config** conversation with Sid — do not assume a code change or pre-tune the threshold.

**Acceptance M0:** with `DEMO_DATA` off in the browser, a fresh profile's Today shows **no** usual-card for a food never eaten (the day-0 seed-food nudge is gone); with a real generated menu present, `menuPrior > 0` for foods actually on the menu; `widgetPayload` resolves an `fdc:` food's real name and kcal instead of a raw id; existing brain tests stay green (165). Add a test in `packages/brain/test` or `packages/menu/test` covering `weekMenuFor` shape if the adapter lands in a package; if it stays app-side, say so and note it is browser-verified only.

## M2 — Backfill logging (log yesterday) — M

**Goal:** a forgotten meal can be logged onto any PAST day of the current week. Future days stay planning-only. ⚠️ **Per D9 this is inert on Sunday and delivers one day on Monday** — the week is Sunday-anchored.

1. **`eventStore.logFood` gains `opts.ts?: number`.** ⚠️ **The obvious implementation collides ids.** Today `let idc = 0` is at **module scope** (:72) and resets on every JS reload; the `Date.now()` component of `` id: `log-${idc++}-${now}` `` is what saves it. A single `const now = opts.ts ?? Date.now()` (natural, since one `now` feeds **both** the id and the ts, :109) makes the id **deterministic** — so after any reload, backfilling the same (day, slot) yields a byte-identical id, `logEvents` filters `!deleted.has(e.id)` (events.ts:84) so one `deleteLog` soft-deletes **both** rows, and `key={item.id}` (Day.tsx:490) collides in React. **Split the two uses:**
   ```ts
   const nowReal = Date.now();
   const ts = opts.ts ?? nowReal;
   // { id: `log-${idc++}-${nowReal}`, ts, … }
   ```
   Also re-point the slot fallback: `slot: opts.slot ?? inferSlot(now, 0)` (:120) would put a backfilled event in **today's** slot. Latent only (all four Day call sites pass an explicit slot) — fix it while you're there.
2. **`tsFor(epochDay, slot)` — UTC, not local.** ⚠️ v1 said "local", which is wrong: `localParts` reads `getUTC*` and computes `epochDay = Math.floor((ts + tzOffsetMin*60_000)/86_400_000)` (time.ts:21-29), and **every** call site passes `tzOffsetMin: 0` ⇒ `epochDay ≡ UTC day`. Build it UTC-side so it round-trips `localParts(ts,0).epochDay === epochDay`:
   ```ts
   const tsFor = (epochDay: number, slot: MealSlot) =>
     epochDay * 86_400_000 + SLOT_TIME[slot] * 3_600_000;   // SLOT_TIME per D11
   ```
   The correct UTC-floor precedent already exists: `dayHourTs` (seed.ts:43-46).
3. **`isPast` — one time frame, and delete v1's "week wrap" caveat.** ⚠️ There is no wrap: `generate.ts:278` emits `days.push({dayOfWeek: d % 7, …})` for `d < 7` ⇒ **`plan.days[i].dayOfWeek === i`, always** (which makes `Day.tsx:96`'s `findIndex` an identity).    const p = localParts(now, 0);

That changes today's behavior near midnight for non-UTC users; note it in the commit body.
